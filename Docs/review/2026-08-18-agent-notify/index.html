1. 로직이 어떻게 되는가

문제: PTY(가상 터미널)는 "명령이 끝났다"를 알려주지 않는다. claude/codex는 셸을 떠나지 않는 하나의 장수 프로세스라서 프로세스 종료도, 새 프롬프트도 완료 신호가 되지 못한다. 그래서 바이트 스트림에 실제로 남는 흔적만 쓴다.

신호 4종 (신뢰도 순)

#신호정체신뢰도지연
1OSC 9 / OSC 777 에이전트가 명시적으로 쏘는 데스크톱 알림 이스케이프 시퀀스 확실 (명시적 의도)즉시
2BEL (0x07) claude의 terminal_bell 알림 채널이 울리는 종소리 높음 (단, 셸 탭완성 실패에도 울림)즉시
3진행 표시 소멸 esc to interrupt 힌트가 스피너와 함께 재렌더되다 끊김 중간 (문구가 바뀌면 죽음)~2초
4출력 정지 에이전트 세션에서 출력이 연달아 흐르다 조용해짐 — 벤더 문구 무관 중간 (보수적 임계값으로 보정)~2초
4번을 왜 추가했나: 처음 구현은 3번 하나에 전부를 걸었다. codex가 승인 질문 화면으로 넘어가며 그 힌트를 지우자 감지가 통째로 죽었고, "이 설계로 진행해도 될까요?"라는 질문을 놓쳤다. 문구는 버전마다 바뀌지만 "출력이 흐르다 멈춘다"는 어떤 에이전트든 예외가 없다.

상태 기계

┌──────────────── noteUserInput() (사용자 키 입력) ────────────────┐ ↓ │ ┌─────────┐ 마커 발견 또는 (에이전트 세션 && 출력 간격 ≤ gapMs) ┌──────────┐ │ │ IDLE │ ─────────────────────────────────────────────────────→ │ BUSY │ ───────┘ └─────────┘ └──────────┘ ↑ │ │ 출력이 idleMs(2s) 동안 끊김 │ ↓ │ ┌────────────────────┐ │ 지속시간 부족 → 조용히 IDLE 복귀 │ 완료 후보 판정 │ └────────────────────────────────────────────────────── │ floor = 마커 봤나? │ │ 예 → 4s, 아니오 → 8s│ └────────────────────┘ │ 통과 쿨다운 3s 내 중복? ─┤ ↓ 아니오 onDone() 발화 ↓ shouldNotifyAgentDone(탭·창·입력) 판단 ↓ ↓ 알림 생략 (사람이 앞에 있음) OS 토스트 + 탭 배지 + 작업표시줄 깜빡임

왜 사용자 입력이 구간을 끊는가

사용자가 빠르게 타이핑하면 키 에코가 연달아 도착한다. 그걸 "출력이 흐른다"로 보면 타이핑을 멈추는 순간이 작업 완료로 오인된다. 그래서 onData(키 입력)에서 noteUserInput()을 호출해 구간을 끊고, 동시에 "이 사람이 방금 여기 있었다"는 근거(sinceUserInputMs)를 기록한다. 이 값이 알림 여부 판단의 핵심 재료다.

2. 2초·4초·8초·1.5초·3초·15초 — 근거

전부 측정된 물리량이 아니라 트레이드오프 선택이다. 각 숫자에는 "낮추면 무슨 일이 생기고, 올리면 무슨 일이 생기는가"가 근거로 붙는다. 근거가 관찰이 아니라 추정인 항목은 그대로 표시했다.

상수값역할이 값인 이유낮추면올리면근거 등급
gapMs1.5s "출력이 이어진다"의 기준 토큰 스트리밍은 수십~수백 ms 간격. SSH 왕복 지연 + 서버 스케줄링 지터를 흡수할 여유가 필요. 스트리밍이 잠깐 끊길 때마다 구간이 쪼개져 지속시간 미달 → 미탐 무관한 출력까지 한 작업으로 이어붙임 → 오탐 관찰 기반 추정
idleMs2s 완료로 판정하는 침묵 길이 claude/codex 스피너는 100ms~1s마다 재렌더. 가장 느린 렌더 주기의 2배 이상이어야 살아있는 작업을 죽었다고 오판하지 않는다. 네트워크 지터·SSH 버퍼링에 오탐 (일하는 중에 완료 알림) 알림이 그만큼 늦음 관찰 기반 추정
minBusyMs4s 벤더 마커를 봤을 때의 최소 작업 시간 4초 미만은 사용자가 화면 보며 기다리는 체감 범위. 이걸 알리면 알림이 곧 무시된다. 짧은 질문에도 토스트 → 알림 피로 짧은 작업 완료를 놓침 순수 판단 (조정 후보)
minStreamMs8s 마커 없이 출력 흐름만으로 판정할 때의 최소 작업 시간 벤더 근거가 없는 판정이므로 의도적으로 minBusyMs의 2배. docker logs -f 같은 스트림이 잠깐 조용해지는 것과 구분하는 완충. 로그 스트림 정지를 완료로 오인 실제 완료를 놓침 (특히 짧은 승인 질문) 순수 판단 (조정 후보)
cooldownMs3s 중복 발화 억제 같은 작업이 BEL과 idle 두 경로로 잡히면 두 번 울린다. idleMs(2s)보다 커야 두 신호를 하나로 묶을 수 있다. 2s + 여유 1s. 한 작업에 알림 2개 연속 작업의 두 번째 완료를 삼킴 구조적 제약 (idleMs 종속)
RECENT_INPUT_MS15s "사람이 앞에 있다"고 보는 시간 입력 직후 15초는 프롬프트를 읽고 반응하는 범위. 이 창 안에서만 알림을 생략한다. 타이핑 직후에도 토스트가 떠서 방해 자리 비운 사용자를 "보고 있다"고 오판 → 이번 사고의 원인 관찰 기반 추정
TAIL_KEEP80자 청크 경계에 걸린 마커 복원용 꼬리 가장 긴 마커가 약 30자(ctrl+c to interrupt + ANSI). 2배 이상 여유. 경계에서 잘린 마커를 놓침 비용 증가 (미미) 최댓값 계산

지켜야 하는 불변식

gapMs (1.5s)  <  idleMs (2s)  <  cooldownMs (3s)
minBusyMs (4s)  <  minStreamMs (8s)
  • gapMs < idleMs: "이어짐" 기준이 "완료" 기준보다 느슨해야 한다. 뒤집히면 연속으로 인정된 출력이 곧바로 완료로 판정된다.
  • idleMs < cooldownMs: 완료를 판정하는 시간보다 억제 창이 길어야 같은 작업의 중복 신호를 묶는다.
  • minBusyMs < minStreamMs: 근거가 약한 판정에 더 긴 증거를 요구한다.

이 불변식은 아직 테스트로 못 박지 않았다. 상수를 만지는 사람이 뒤집을 수 있는 구멍이다 — 6장에 남은 위험으로 적었다.

3. 휴리스틱이란 무엇인가

휴리스틱(heuristic) = 정답을 보장하지 못하지만 대부분의 경우 충분히 잘 맞는 경험적 규칙. 정확한 답을 구하는 비용이 지나치게 크거나 아예 불가능할 때 쓴다. 핵심은 "맞다/틀리다"가 아니라 틀리는 방향과 그 대가를 내가 고르는 것이다.

왜 여기서는 휴리스틱이 불가피한가

정확한 답을 구하려면 원격 프로세스의 상태를 알아야 한다. 그러려면 ① 원격에 에이전트를 심거나 ② 에이전트 CLI가 완료 API를 제공해야 한다. 우리가 가진 것은 SSH PTY를 통해 흘러오는 바이트 스트림 하나뿐이다. 그 안에서 "일이 끝났다"를 추론하는 것 — 이것이 휴리스틱이다.

이 코드가 쓰는 휴리스틱과, 각각이 틀리는 방향

휴리스틱가정틀릴 때 (오탐)틀릴 때 (미탐)완충 장치
진행 힌트 소멸 = 완료 CLI는 일하는 동안 힌트를 계속 재렌더한다 렌더가 1회 지연되면 완료로 오판 문구 변경·화면 폭 부족으로 힌트 미출력 idleMs 2초 + 출력 정지 경로(4번 신호)로 이중화
출력 정지 = 완료 에이전트는 응답을 연달아 뱉는다 긴 로그 스트림이 조용해질 때 토큰 간격이 1.5초 넘게 벌어지는 초저속 응답 에이전트 세션 확정 필요 + minStreamMs 8초
명령 에코 = 에이전트 세션 프롬프트 뒤의 codex는 실행 의도다 로그 본문에 이름이 스칠 때 (→ 프롬프트 위치 요구로 차단) tmux 복원 세션처럼 에코를 못 본 경우 벤더 마커·tokens used·⏎ send로 우회 확정
BEL = 완료 에이전트만 벨을 울린다 셸 탭완성 실패, printf '\a' 알림 채널을 끈 사용자 "작업 중이었을 때만" 인정
15초 내 입력 = 사람이 앞에 있음 방금 타이핑했으면 화면을 본다 타이핑 후 즉시 자리를 뜬 경우 → 알림 생략 — 탭 배지는 조건 없이 항상 남긴다
설계 원칙: 이 기능에서 미탐(놓침)은 오탐(과잉 알림)보다 훨씬 비싸다. 놓치면 에이전트가 승인 질문 앞에서 몇 시간을 멈춰 서 있고, 과잉이면 토스트 하나가 거슬릴 뿐이다. 그래서 애매하면 알리는 쪽으로 기울였고, 대신 배지·표시등으로 사용자가 스스로 검증할 수 있게 했다.

리뷰 과정에서 스스로 잡아 고친 결함 6개

  1. 관문 정규식 이중 관리 — 지문 목록과 사전 필터가 따로 있어, 지문을 추가하며 필터를 빠뜨리면 그 지문이 영원히 매칭되지 않는데 테스트는 통과했다. 한 자리에 묶고 관문은 생성하게 바꿈.
  2. 벤더 이름만으로 세션 판정 — INFO starting codex-service 로그 한 줄로 에이전트 세션 확정 → 이후 로그가 멈출 때마다 알림. 프롬프트/런처 위치에서만 인정하도록 좁힘.
  3. 관문 이중 스캔 — 8KB를 두 번 훑고 있었다. 세션 확정 여부에 따라 좁은 관문으로 교체 (7.8µs → 3.5µs).
  4. 알림 판단이 React 콜백에 박혀 검증 불가 — 순수 함수로 추출하고 경계값까지 테스트 6개.
  5. 탭을 닫아도 배지 상태가 남음 — 죽은 tabId 정리 추가.
  6. 권한 거부를 캐시 — 나중에 OS에서 알림을 켜도 재시작 전까지 영원히 조용. 허용만 캐시하도록 수정.

5. 성능 실측

감지기는 모든 PTY 바이트가 지나가는 경로에 있다. 여기서 낭비하면 cat 한 번에 UI가 버벅인다. 8KB 청크(Rust reader 버퍼와 동일) 기준, Intel Ultra 7 155H.

6. 남은 위험 (숨기지 않음)

  • 임계값 불변식이 테스트로 고정되지 않았다. 누가 gapMs를 3초로 올리면 조용히 오탐 기계가 된다. 불변식 테스트를 추가하는 게 다음 작업으로 맞다.
  • UI 배선은 테스트가 없다. 순수 로직(감지기·정책)만 27개로 덮었다. TerminalView의 OSC 핸들러 등록·표시등은 실기기 확인에 의존한다.
  • 실제 codex/claude 출력으로 4번 신호를 검증하지 못했다. 테스트는 내가 재현한 프레임 문자열이다. 헤더 ● 작업 중 표시등을 넣은 이유가 이것 — 실사용에서 형님이 즉시 검증할 수 있게.
  • 에이전트 세션에서 docker logs -f를 8초 이상 돌리다 멈추면 완료 알림이 뜰 수 있다. 의도한 트레이드오프(미탐 > 오탐 회피)다.
  • Windows 토스트 권한은 첫 알림 때 한 번 확인된다. 거부 상태면 배지만 남는다.

8. 이게 어떤 커밋 방식인가

형님이 말한 흐름 = "푸시 전 자체 diff 리뷰 → 이해 검증 → 논리 단위로 쪼개 커밋". 업계에 이름이 붙어 있는 세 가지 관행의 조합이다.

① Pre-commit self-review (자체 리뷰)

커밋 전에 자기 diff를 처음 보는 리뷰어처럼 읽는 관행. Google의 코드 리뷰 문서에서 "리뷰 요청 전 스스로 먼저 검토"로 권장되고, git에서는 git add -p(조각 단위 스테이징)로 강제된다 — 한 조각씩 보며 담아야 하니 diff를 안 읽을 수가 없다. 이 웹페이지가 그 역할을 하고 있다.

② Atomic commits (원자적 커밋)

커밋 하나 = 작업 하나 / 수정 하나. 되돌릴 때 다른 변경을 함께 잃지 않고, 체리픽·git bisect가 의미를 갖는다. "퇴근할 때 한 번" 같은 습관을 버리고 논리 블록이 완성될 때 커밋한다. 한 기능에 여러 파일이 필요하면 그건 한 커밋이 맞다.

③ Conventional Commits (커밋 메시지 규약)

<type>(<scope>): <description> 형식. feat은 SemVer MINOR, fix는 PATCH, BREAKING CHANGE는 MAJOR에 대응해서 CHANGELOG와 버전 산정을 자동화한다. 이 저장소는 이미 이 규약을 쓰고 있다 — feat(cicd): ..., chore: bump version to 0.4.0, build: update prebuilt binaries.

정리하자면 형님이 말한 방식은 self-review → atomic commits → conventional commit messages이고, 각 커밋이 그 자체로 빌드/테스트가 통과하게 순서를 잡으면 bisectable history(이진 탐색 가능한 이력)까지 얻는다.

이번 변경의 커밋 계획 (4개, 순서 중요)

의존성 → 순수 로직 → UI 배선 → 문서 순서로 쪼갠다. 이 순서면 중간 커밋에서도 빌드와 테스트가 통과한다.
